# 后续开发顺序

这些是后续任务，不是本次已经完成的功能，也没有安排后台执行。

## P0联调

在有写入权限的连接或本地Git环境中完成上游导入及升级分支提交；确认上游使用条件。读取真实资料目录，抽查白歌父记录和相关效果牌是否与当前客户端一致。配置一个真实模型服务进行最小请求，记录超时、截断、建议拦截比例与费用，而不是预设响应速度。

## P1画面与状态

先用公开且有使用权的截图/视频核对画面区域，再在实际Windows客户端测试分辨率、缩放和窗口模式。建立卡牌ID与图标匹配，识别输出仍应包含未知项。增设画面变化检测与稳定区去抖，关联商店、手牌、计数事件；检测到变化立即撤回建议，再选择是否请求模型。避免每帧调用完整大模型。

## P1白歌局部计算

把已核实的合成、费用、即时奖励、复制目标与手牌变化建成可测试的状态转移函数。只在机制已明确的范围枚举短操作序列；未知随机分布使用显式假设和敏感性比较，不输出虚假的精确概率。将操作计算结果提供给模型作策略取舍，不把任意加权分数包装成真实胜率。

## P2策略质量

使用同一批决策发生前的局面，对照纯本地提醒、模型建议、混合校验三种模式。记录可执行性、关键前提遗漏、无证据断言、响应是否及时和局面发生变化后是否撤回。对照时不得提前泄漏后续来牌或战斗结果。

真实战斗结果只是一部分证据；不能因一局获胜就证明所有建议正确。先修复识别与规则问题，再调整策略提示。形成稳定性证据后才考虑自动触发覆盖、更多棋手和打包发布。
